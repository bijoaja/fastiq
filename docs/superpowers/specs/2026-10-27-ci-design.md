# CI — Design Spec (fastiq)

Date: 2026-10-27
Status: Draft, awaiting approval (no implementation yet)

## 1. Background

fastiq has tests (60, pytest) but no CI, no linter, and no hook, so nothing checks a PR before it is
merged. Facts that shape the design:

- `pyproject.toml`: `requires-python = ">=3.12"`, a `dev` dependency group (pytest,
  pytest-asyncio, aiosqlite, httpx), and a committed `uv.lock`.
- `uv sync --frozen` then `uv run pytest` passed with 60 tests on Python 3.12 and 3.14 (Windows),
  with a lone Starlette deprecation warning.
- The tests need `DATABASE_URL` and `SECRET_KEY`. With no `.env` and no variables the suite fails at
  collection; with both set in the environment it passes (see the test-structure spec, finding 1).
- `.env` is tracked in git, so a plain checkout contains it, but CI must not depend on it.
- The repo is public, default branch `main`.

## 2. Goals

- Every PR is tested on each push; `main` is tested again after every merge.
- The lockfile stays consistent with `pyproject.toml`.
- Tests run on the lowest supported Python and on the newest one in use.

## 3. Non-goals and anti-goals

Non-goals: building or pushing the Docker image, deployment, lint or format, coverage thresholds,
running against a real Postgres, changing dependency versions.

Anti-goals: a check that passes only because it read the tracked `.env`; skipping or xfailing tests
to get green; dropping a Python version to hide a failure.

## 4. Decisions

Made by the user:
- One workflow per repo, on pull requests and pushes to `main`.
- `.github/workflows/ci.yml` is allowed to ship into projects created by `pyartisan new fastapi`, because that command clones the template unchanged. No exclusion mechanism is built.
- Untracking `.env` is a separate small PR (see the test-structure spec, finding 2).
- Specs live in this repo's `docs/superpowers/specs/`.

My calls (the user can overrule any of them):
- Matrix: `ubuntu-latest` x Python `3.12` (the minimum) and `3.14`. Linux only; the template runs in Linux containers and the suite has not been run on Linux yet (see risks).
- Steps: `uv lock --check`, `uv sync --frozen`, `uv run pytest -q`.
- The job deletes the checked-out `.env` (`rm -f .env`) before running tests, then sets `DATABASE_URL=sqlite+aiosqlite:///:memory:` and `SECRET_KEY` to a fixed non-secret test value as environment variables. Reason: `app/config/settings.py` reads `env_file=(".env", ...)`, and `.env` is tracked, so without the delete the file silently fills any variable the job forgets to set and the "does not read `.env`" guarantee cannot be tested. This also means CI does not depend on whether the separate `git rm --cached .env` change is merged (see the test-structure spec, finding 2).
- Aggregate job `ci-ok` that `needs` the matrix job; the ruleset requires only this name.
- Naming is the same in all three repos: the file is `.github/workflows/ci.yml`, the workflow `name:` is `ci`, and the aggregate job is `ci-ok`.
- Triggers `pull_request`, `push` on `main`, `workflow_dispatch`; `permissions: contents: read`; a `concurrency` group per ref cancelling older runs.

## 5. Jobs

| Job | Runs on | What it does |
|---|---|---|
| `test` | matrix: Python 3.12, 3.14 | checkout, `rm -f .env`, install uv, `uv lock --check`, `uv sync --frozen --python <v>`, `uv run pytest -q` with the two environment variables |
| `ci-ok` | `ubuntu-latest` | `needs: [test]`, `if: always()`, fails unless `test` succeeded |

## 6. Making the check mandatory

A workflow alone does not block a merge. The owner creates a ruleset on `main` in the GitHub UI:
require a pull request, require the status check `ci-ok`, and decide on admin bypass (by default an
admin can bypass; turning that off also stops direct pushes by the owner). The check name only
appears in the list after the workflow has run once, so: workflow PR first, merge when green,
ruleset afterwards. Claude does not change repository settings. A direct push to `main` triggers CI
only after the code is in.

## 7. Risks

- The suite has only run on Windows. Linux may differ (paths, line endings, SQLite behavior). A first-run failure there is a finding to fix, not a reason to loosen CI.
- Fix policy for such a failure: a bug in `app/` is fixed in its own issue and PR; a bug in a test or in `conftest.py` is fixed in the workflow PR. The rule "no file under `tests/` changes" in the test-structure spec applies to that spec's own work only, not to fixes forced by CI. In both cases no test is skipped or xfailed, and the ruleset is not enabled until the run is green.
- Order of work: (1) the workflow PR, which itself triggers the workflow and must be green; (2) a separate PR for the `CLAUDE.md`/README mention of CI; (3) the owner creates the ruleset in the GitHub UI. The throwaway-branch checks in section 9 need pushes and PRs on GitHub: the builder may run them only after asking the owner each time, and closes the PRs afterwards.
- `conftest.py` overrides `event_loop` at session scope, which newer pytest-asyncio releases deprecate. `--frozen` keeps the locked version, so CI is stable until the lock is updated. When someone runs `uv lock --upgrade`, expect this to surface.
- `uv lock --check` fails if `uv.lock` is stale relative to `pyproject.toml`. That is intended: regenerate with `uv lock` and commit.
- Python 3.14 resolved today; a later dependency release without a 3.14 wheel would show up here first.

## 8. Details decided at implementation time

Versions of `actions/checkout` and `astral-sh/setup-uv` (look up the current major with `gh api`),
whether to pin the uv version, exact YAML.

## 9. Acceptance

- The workflow PR triggers the workflow itself; both matrix cells and `ci-ok` pass with 60 tests each.
- Deleting `SECRET_KEY` from the job environment on a throwaway branch makes the job fail with `Field required` (it can, because the job removes the checked-out `.env`). Try once, close the PR.
- Making `uv.lock` stale on a throwaway branch makes `uv lock --check` fail.
- After the owner enables the ruleset, the merge button is disabled while `ci-ok` is red.
- `CLAUDE.md` or the README mentions CI and the local commands.

## 10. Left to the builder

YAML layout, step wording, caching (`setup-uv` has built-in cache support), and whether to add `--strict-markers` or similar pytest flags.
